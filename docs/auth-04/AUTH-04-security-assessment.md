# AUTH-04 security assessment

Date: 2026-10-23. Scope: branch `codex/auth-02-player-ownership`, base commit `d03faab`; local changes in this milestone are not deployed. This assessment distinguishes code/local database evidence from hosted OAuth behavior.

| Severity | Finding and evidence | Impact / disposition |
| --- | --- | --- |
| HIGH release blocker | OAuth redirects previously used the request `Host` directly. A direct `requestOrigin()` test with `evil.example` returned `https://evil.example`. `trustedAuthOrigin()` now permits development loopback or an exact entry in `ATLAS_AUTH_ALLOWED_ORIGINS`; production-mode loopback also requires an explicit entry. Google, callback and logout routes return 400 for an unapproved origin. `test:auth` passes hostile/approved/preview cases; native Next HTTP checks no redirect leaves its local origin. | Code fixed locally. Vercel environment values and Supabase redirect allowlist could not be inspected; configure and verify them before release. A missing allowlist intentionally blocks production OAuth. |
| MEDIUM | Same-document identity replacement is not a supported UI path, but `useAccountProfile` is keyed by enabled/retry and `SavedVocabularyProvider` retains words when disabled. Current sign-in and logout navigate the whole document; the real A→B delayed-response browser race was not run. See AUTH-03 audit. | Real-provider account switching and a delayed-request race remain unverified. Do not claim cross-account UI isolation beyond the tested full-navigation path. |
| LOW | The sign-in anchor has no pending/duplicate-click state. | AUTH-03 UX item remains open; no evidence of an authorization bypass. |

The active `/api/[...path]` route asks Supabase `auth.getUser()` for the user and passes only its verified UUID to the trusted handler. It rejects anonymous/invalid IDs, client-supplied player selectors, cross-origin POSTs, and client-supplied XP. A server-only admin client can bypass RLS, so explicit UUID scoping is essential; local API/PostgREST tests cover profile, expedition, reward and checkpoint isolation. Client responses are private/no-store. Supabase SSR cookies use HttpOnly, SameSite=Lax, and Secure when `NODE_ENV=production`. The callback uses Supabase's code exchange and redirects only to `/` or `/auth/error`; query `returnTo` does not control the destination.

Local security evidence: `pnpm test:auth`; `pnpm test:auth:http` with Brave mobile/desktop fixture; `pnpm test:auth02` (19 real PostgreSQL/PostgREST checks); `pnpm test:auth02:http`. Invalid/expired signed fixture tokens and CSRF attempts produced no player writes. A scan of 30 `.next/static` files found zero occurrences of the configured server secret. [Local check record](../../output/auth04/local-checks.json). These tests do **not** prove real GoTrue refresh/revocation, Google PKCE/state handling, Vercel host routing, or deployed cookie behavior. No raw token or key is included in these reports.

The current configured Supabase `/auth/v1/settings` read returned Google enabled. That is provider availability, not successful consent or callback verification. The historical production alias redirected `/api/health` to Vercel SSO (302), preventing application-level inspection. Vercel project detail/deployment queries returned 403 for team `phuctptse183992-1459s-projects`; the required team authorization operation was unavailable in this session.
